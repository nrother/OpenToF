# OpenToF — Decisions

The product and engineering decisions behind OpenToF and, where it isn't obvious, why. Dates say when a decision
was made or last changed. Anything not covered here is an **open question** (see the end): ask the product owner
rather than assume.

The BLE interface itself is specified in [`PROTOCOL.md`](PROTOCOL.md); this file only records the choices behind it.

## Product scope

- Name `OpenToF`; Dart package `opentof_app`; application/bundle ID `com.opentof.app`.
- Flutter app for **Android 10+ (API 29) and iOS 15+**. English and German (follows the device language). Metric
  units only. No accounts, no cloud, no history browser.
- One sensor per app, but device selection stays multi-sensor friendly.
- **Jump height is shown as "beta"** (h = g·t²/8, g = 9.81 m/s²): it follows from the flight time, but nobody has
  checked it against real heights.
- **No raw-data streaming** in v1: the hardware path isn't there yet. The code stays open for adding it later.
- Debug builds contain a **simulated sensor** (`MockSensor`) behind the same interface as the real one, so the app
  can be developed and tested without hardware.

## Sensor ↔ app protocol (protocol 1, 2026-09-26; sleep command 2026-10-09)

- **The sensor sends events with its own timestamps, not durations.** The app computes flight time, time on bed,
  totals and height. Why: Bluetooth delays then never affect the measured times, and the app can recompute
  everything when a value is corrected.
- **Two stages (provisional, then final within ~200 ms) plus retractions.** Why: the athlete needs the beep right
  away, but a precise landing time needs a little more data. Agreed with the algorithm team as "algorithm
  interface v1".
- **Confidence, reasons and custom fields are optional and self-described** (JSON in read-only characteristics). Why:
  new algorithms can add values without an app update; the app shows whatever the sensor declares.
- **No replay buffer**: the connection is assumed to stay up; events while disconnected are lost and shown as
  missed. Dropped from the algorithm team's proposal as well: a live-state characteristic (provisional events cover
  it), device health, a debug stream. Possible later: landing position / landing type as custom fields.
- **Boot counter** instead of a clock sync, so the app notices a restarted device clock.
- **Sleep command** as a new optional characteristic within protocol 1; its presence is the feature flag, so no
  protocol version bump was needed.
- **Scan by Jump service UUID**, not by name (names can be changed).
- **BLE library: flutter_blue_plus with `License.nonprofit`.** The product owner confirmed OpenToF qualifies
  (2026-09-21). If that ever changes (e.g. commercial distribution), change the license in `ble_sensor.dart` or
  switch libraries.

## Routine

- States: Idle → Running → Complete or Cancelled. A finished routine (table, total, export) **stays on screen until
  the next Start**; there is no "back to idle".
- **Start** is only enabled while the athlete is jumping: the last landing was at most the inactivity timeout
  (default 4 s) ago. Otherwise it is greyed out with a hint.
- **Jump #1 is the jump in progress when Start is pressed, i.e. the first landing after Start** (2026-10-14). The
  jump that had already landed before Start does not count. Before 2026-10-14 the jump that had just landed was #1,
  which was a misunderstanding of the intended rule.
- The inactivity timer runs from the Start press and restarts on every landing. Running out cancels the routine
  (progress kept and exportable). Cancel is always available while running.
- **Jumps per routine** is a setting (default 10, minimum 1, technical maximum 999; 2026-09-22). It is fixed when a
  routine starts. A 1-jump routine ends on the first landing after Start.
- **Disconnect** pauses the routine (progress kept) while the app reconnects. The inactivity timer keeps running, so
  a disconnect longer than the timeout cancels it.
- No manual corrections: every detected jump counts. A jump the sensor retracts is removed again (also jump #1).
- Routine timing uses the phone's receive time of the landing event.

## Feedback, chart and export

- **Sound:** a beep on the landing of every routine jump except the last, which plays only a distinct final sound.
  Both have their own toggle. Pressing Start is silent. No sound for connection errors. The tones are generated by
  `app/tool/generate_sounds.dart`.
- **Chart:** one bar per jump (height = flight time) over a time-based window (30 s / 1 min / 5 min, default 1 min),
  drawn with our own `CustomPainter` because fl_chart can't do a time-proportional x axis. Clear empties it.
  **Pause** only freezes the view; jumps and events keep being recorded (2026-09-22).
- **Chart markers** (automatic, with a legend): sensor connected/disconnected (real transitions only, not every
  reconnect attempt), routine started/stopped (one stop marker whatever the reason), implausible jump (2026-09-24).
- **Implausible jumps:** a flight time over 2.5 s is almost certainly a glitch. It is left out of the routine, the
  last-jump display, the chart bars and the CSV, but gets a chart marker so it is visible while debugging. The
  threshold is a constant (`maxPlausibleFlightSeconds` in `jump.dart`), not a setting.
- **Uncertain jumps:** a reason bit or a confidence below 50 → "?" icon with the confidence and reasons as tooltip.
- **CSV export** via the OS share sheet only, for a finished (complete or cancelled) routine or the last 30 s / 1 min /
  5 min of jumps (2026-09-26). Columns: jump number, flight, contact, total, height (beta), missed-event flag,
  provisional flag, confidence, reasons, one column per custom field. **No total row** (2026-09-30), so every row is
  data. Time-range exports contain `routine_start`/`routine_stop` marker rows; routine exports don't need them.
  Format: seconds and meters with 3 decimals, `.` separator, CRLF, English headers, empty cell = unknown.
- **Jump display options** (off by default, 2026-09-26): time on bed and total jump time (line under the last jump
  plus table columns); "more jump details" with a checklist of the sensor's values (stored as *hidden* ids, so values
  a new algorithm adds show up by default) and a details sheet when tapping a jump.

## Settings and screens

- **The app always starts on the main screen** (2026-09-22). Without a paired sensor it shows a card that opens
  Settings.
- Settings: pair/scan, rename and unpair the sensor, routine (timeout 1–30 s, jumps per routine), sounds, chart
  window, jump display, theme (System/Light/Dark), LED signals, version.
- **Sensor page** (tap the paired sensor, 2026-09-26): battery and time remaining, device info, protocol version and
  boot count, the detection algorithm's name and declared values, and "Put sensor to sleep".
- **Version warning** in Settings and on the sensor page when app and firmware MAJOR.MINOR differ; none while the
  firmware version is unknown.
- **Battery time remaining** is estimated on the phone from recent readings (least-squares slope; needs ≥ 5 min and
  ≥ 1 % drop; a rising level resets it). In memory only.
- **LED signals page** (2026-10-09) explains the orange status LED and the red charge LED with a picture of each blink
  pattern. Its texts and timings are written into the app, so they must be changed together with the firmware
  (`firmware/README.md`, "LED signals").
- **In-app changelog** (2026-10-09): *Settings → Version* shows the root `Changelog.md` in two tabs, App and Sensor
  firmware. The file is the single source; the app bundles a copy (see "Releasing" in the root README).
- **While the sensor sleeps on the app's command** the status reads "Sensor asleep" and the app retries every 10 s
  instead of 2 s. This state is only known in memory and only after the app's own command.

## Android and iOS

- Android: a **foreground service** keeps the BLE connection alive while a sensor is paired. Because of it there are
  three ways to quit (2026-09-21): an Exit button in its notification, *Settings → Exit app* (with confirmation), and
  pressing Back twice on the main screen. Exiting disconnects, stops the service and closes the app; the pairing is
  kept.
- iOS: background BLE is best effort; there is no exit option (not allowed by the platform). The Bluetooth permission
  text is English only for now.
- Android permissions: `BLUETOOTH_SCAN` (neverForLocation) + `BLUETOOTH_CONNECT` on Android 12+, legacy Bluetooth +
  location on 10/11. Before scanning, the app asks to turn Bluetooth on if it is off.
- `permission_handler` stays on 12.x: 13.x needs compileSdk 37, which the current Android Gradle plugin doesn't
  support. Revisit when Flutter moves to compileSdk 37.

## Branding (2026-09-21, logo replaced 2026-09-26)

- The sources live in the root `img/` (shared by app, README and docs): the logo (`opentof-logo.svg`, blue `#0153E3`
  with a red `#DE2237` bed marking), the lettering (`OpenToF_Wordmark.png`) and versions derived from them by
  `img/make_wordmark.py`, including dark-theme versions with a lighter blue `#5B9BFF` for contrast on the dark
  surface `#121318`.
- The app only holds derived copies, made by `app/tool/generate_branding.ps1` (then `flutter_launcher_icons` and
  `flutter_native_splash`). The launcher icon stays the light version.
- The theme seed colour is the logo blue. The web target (`app/web/`) is not branded; it is only used for trying the
  UI in a browser.

## Firmware

- **Board and stack:** Seeed XIAO MG24 Sense, Silicon Labs Arduino core with the **"BLE (Arduino)"** stack (the
  ArduinoBLE API), IMU (LSM6DS3TR-C) via the Seeed library.
- **One sketch with pluggable detectors** (2026-09-22). `DEMO_MODE 1` sends simulated jumps instead of reading the IMU.
  Why: a separate demo sketch drifted out of date; the demo mode in the real sketch gets every change for free.
- **Algorithm selection by commenting `#include` + `typedef` pairs in and out** at the top of the `.ino` (2026-09-22).
  A numeric selection macro was tried and felt overbuilt.
- **Code lives in headers** (`config/`, `algorithms/`, `core/`); the `.ino` only has `setup()`/`loop()`. Why: the
  Arduino IDE generates prototypes for functions in `.ino` files and breaks when they use sketch-defined types.
- **IMU profiles** (416 Hz / ±8 g and 833 Hz / ±16 g) are chosen at compile time, by the detector or
  `IMU_USE_HIGH_RATE_PROFILE`. There is no BLE setting for it because the protocol has no configuration
  characteristic.
- **The IMU is read as six 2-byte register reads per sample**, not one 12-byte burst: the burst read fails on this
  board (found 2026-09-22). This limits the real rate to ~285 samples/s with the 833 Hz profile, which is enough for
  jump detection.
- **No charging state over BLE** (2026-09-22): the charger only drives the red LED and the MCU can't read it. The
  product owner doesn't want a guessed value, so the red LED is the charging indicator.
- **Deep sleep** (2026-10-09): after 1 minute (`SLEEP_AFTER_IDLE_MS`; 5 minutes felt too long) without a connected app
  and without a jump, the sensor sleeps (EM4). It never sleeps by itself while an app is connected. The board doesn't
  wire the IMU interrupt pins, so a timer wakes the MCU every 3 s to check the IMU's wake-up flag. Waking up for real
  is a normal start (boot counter +1, app reconnects); the 3 s checks don't count as starts. Off in `DEMO_MODE`.
- **LED signals** (2026-10-09): the orange LED blinks slowly while waiting for the app, is on while connected, and
  has short patterns for going to sleep, woken up and start-up failure. Full table: `firmware/README.md`.
- Unverified engineering choices: gyro range ±500 dps, connection interval 7.5–15 ms, advertising interval 100 ms.

## Open questions

- Real GATT UUIDs (placeholders in app and firmware).
- Whether custom-field names and reason texts should be translated (currently English from the sensor; the app could
  map known `id`s).
- Very long contact times (standing still, then bouncing) are reported as they are; should there be a cap?
- Whether the hardware revision string (`0.1`) is right for the real board.
- Whether a sleeping sensor should be found with `autoConnect` or a back-off instead of a 10 s direct connect every
  10 s (costs some phone battery; needs testing on hardware).
- Min OS versions (Android 10 / iOS 15) against the devices gyms actually use.
